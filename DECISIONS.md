# Key decisions

Short log; newest last. Why, not what.

1. **Inventory-based detection over network banner scanning.** An agent reports installed packages; matching happens server-side against OSV. Banner/version guessing is the main source of Tenable/Qualys noise. Network scanning may come later, gated on verified ownership.
2. **OSV.dev as primary advisory source.** One schema covering Debian, Ubuntu, Alpine, RHEL-family, SUSE, PyPI, npm, Go, crates etc., with distro-native fixed versions (backport-aware). Mirrored locally (bulk zips) so detection is fast, offline and auto-updating.
3. **Match distro packages by source package name**, which is what distro advisories reference. Agent must report source names (dpkg `${source:Package}`, rpm SOURCERPM, apk origin).
4. **Refuse to guess.** Unknown ecosystem or unparseable version → no finding (and later a data-quality metric), never a fuzzy match.
5. **Accuracy is tested against OSV itself.** `tests/fetch_fixtures.py` stores real OSV records plus OSV API answers; tests require exact agreement.
6. **Stack:** Python 3.14 + FastAPI 0.162 + SQLAlchemy 2.1 + Pydantic 2.14 (uv). SQLite in dev/tests, Postgres in prod. React + Vite + TS SPA for the UI (logged-in app, no SEO need → no SSR framework).
7. **Remediation never runs shell from the server.** Jobs are closed descriptions (manager + validated package names/versions); the agent maps them to fixed argv templates. A compromised server can't turn the fleet into RCE beyond "upgrade these packages", and only on hosts that opted in locally (`enroll --allow-remediation`).
8. **Reversible or not at all.** The agent saves a rollback package (apt/apk cache or download, sha256 recorded) for every package before changing anything, and aborts if it can't. Health checks (systemd units) run before and after; failure → automatic rollback → verify versions restored. Rollback failure is reported as `rollback_failed`, never swallowed.
9. **Success = proof, not a claim.** A job is `succeeded` only when the next inventory shows its findings resolved; otherwise `not_fixed`.
10. **Trust ladder + canaries.** Org mode suggest → approve → auto. Auto changes land on ring-0 canaries first; the broad ring waits for a canary success that has soaked N hours, and any failure of that change anywhere halts rollout.
11. **Dev guard:** until `NIMSTEAD_ALLOW_PRODUCTION_REMEDIATION=1`, jobs only go to assets enrolled with a sandbox token.
12. **Evidence = hash-chained ledger + Ed25519-signed packs** verifiable offline with a shipped script; the server refuses to sign if the chain fails verification. Time-to-remediate is measured from first detection to the first inventory proving the fix (stated in each pack).
13. **Security review (Opus) round 1 fixed** ("dnf removed" below is superseded by 16)**:** pinned signing-key fingerprint for offline verification; stale-job sweep + late reports accepted; outcomes persisted on the agent before reporting; rollback artefacts copied into our own dir and hash-checked before use; dry-run refuses transactions touching unplanned packages; `--no-remove`; kill switch and canary re-checked at dispatch; broad ring pinned to canary-proven versions; enrol tokens expire (30 d) and revoke; asset delete; Origin check, 10 MB body cap, timing-safe login, no-redirect agent HTTP. dnf removed until proven in a sandbox.
14. **Known ledger limit:** a DB-level attacker can still rewrite or truncate the whole chain and have the server sign it. Mitigations now: lifecycle timings come from the ledger (not the mutable findings table), and every pack carries `chain_head` so successive packs expose a rewritten history. Next: periodically signed checkpoints stored off-database / RFC 3161 timestamps.
15. **Remediation is apt-only for now** (superseded: apk and dnf by 16, zypper by 25)**.** The first real-host run (Debian 13 WSL sandbox) showed installed versions are usually superseded in the archive and absent from the cache, so no pristine rollback copy exists. For apt the agent now rebuilds the installed package from its files + dpkg metadata (native dpkg-repack via `dpkg-deb`), capturing the exact prior state; proven in the sandbox (upgrade verified by inventory; forced service failure rolled back with versions restored). Alpine has no equivalent we trust yet (no historic archive, apk v2/v3 format split) and dnf is unproven, so both are detection-only and the server refuses to plan them.
16. **apk and dnf rollback = snapshot.** Neither ecosystem keeps old builds, so before a change the agent archives every file the planned packages own plus the package database (`/lib/apk/db` + `/etc/apk/world`, or `/var/lib/rpm`), sha256-recorded. Rollback removes files the new version added, restores the archive and the database, and verifies versions. This is only sound because the dry run proves the transaction touches nothing outside the plan (on Alpine it correctly refused openssl/zlib fixes that also needed musl). `apk add` would also pin packages into the world file, so the world file is restored after every apply. Proven on Alpine 3.21 (injected failure) and AlmaLinux 9 (real service failure) in disposable VMs.
17. **Windows: OS detection via MSRC, no remediation; third-party apps: see 22** (remediation superseded by 22: one cumulative update, reversible by DISM)**.** The OS build is matched against MSRC FixedBuild per product: exact and low-noise. Third-party Windows apps have no reliable advisory source keyed by what's installed (CPE matching is the noisy Tenable/Qualys approach we reject). Windows remediation can't be tested here: Windows Home has no Hyper-V or Windows Sandbox, so a disposable Windows VM needs a hypervisor and an image only the user can provide. Per the hard rule (test only in sandboxes), it isn't built.
18. **SSO needs proof of domain ownership.** An org's SSO only routes emails on domains verified by a DNS TXT record (`_nimstead-verify.<domain>`, an HMAC of org + domain under the server key, so nothing extra is stored). Unverified claims can't block the real owner, and a domain verified by one org can't be taken by another. The client secret is Fernet-encrypted at rest; plaintext is refused, never used silently. "Require SSO" keeps password access for admins only, as a recorded and alerted break-glass, so a broken IdP can't lock an org out.
19. **State that must hold across API workers lives in the DB:** failed-login throttle, per-asset inventory rate limit, and SSO pending logins (single use, expiring). No in-process dictionaries remain.
20. **Dependencies join the plan explicitly.** When the dry run refuses a fix because it needs other packages (e.g. openssl → musl), the user can re-plan "including musl". The dependencies are then snapshotted, rolled back and verified with the fix. Nothing is expanded silently.
21. **Application dependencies come in as CycloneDX SBOMs** (purl → OSV ecosystem), kept separate from agent OS inventory so neither upload wipes the other. Maven, NuGet and RubyGems comparators meet the same bar as the distro ones: exact agreement with the OSV API on real packages (log4j-core, jackson-databind, Newtonsoft.Json, rack, nokogiri…).
22. **Windows remediation = one cumulative update, reversible by DISM.** The agent installs exactly the KB that reaches the highest fixed build, via the Windows Update Agent as SYSTEM; Windows Update must offer exactly that update first. The job is a state machine persisted across reboots (install → reboot → verify build + health → done, or remove the newly added RollupFix package with DISM → reboot → verify the original build). DISM's transient "servicing busy" errors right after boot are retried (seen for real: 0x80010108). A permanent package or a build that doesn't return is `rollback_failed`, loud. Proven on Windows Server 2025 in a disposable VirtualBox VM (`sandbox/winvm.py`, `wine2e.py`). Gotchas found there: VirtualBox 7 NAT blocks guest→host localhost unless `--nat-localhostreachable1 on`; guest control mangles quoting (use `-EncodedCommand`); unattended setup reboots hang under Hyper-V's NEM backend (auto-reset).
23. **Production keys live in Vault, checkpoints in object-locked S3.** Vault transit signs evidence (Ed25519, so offline verification is unchanged), encrypts SSO secrets and HMACs domain tokens; the key never leaves Vault and failures are loud (no silent fallback to local keys). Checkpoints are written with COMPLIANCE-mode object lock, so even the bucket owner can't delete or shorten them. Proven against real Vault and an S3 gateway (MinIO OSS is archived; Versity's S3 gateway was used).
24. **Windows third-party apps: a curated CPE map, never fuzzy matching.** `winapps.py` maps ~18 widely deployed apps from a strict full-match on the registry DisplayName (plus Publisher where the name is generic, e.g. "Git", "Python", "Zoom") to an exact NVD `vendor:product`, with a per-product version normaliser. NVD's CPE match data for only those CPEs becomes OSV-shaped `WinApp` advisories (ranges translated as introduced/fixed/last_affected); an app not in the map is inventory and is never compared. Why not match any DisplayName against all CPEs: that is the Tenable/Qualys noise this product exists to avoid (name collisions like "Chrome Remote Desktop", wrong editions, vendor-name drift). Dropped on purpose, not approximated: Java 8 (registry 8.0.4310.10 vs NVD "1.8.0 update431"), Eclipse Temurin (no CPE exists), matches with no end bound, exclusive start bounds, pre-release/non-numeric versions, mobile/macOS/Linux targets, classic-track Acrobat, AND-configurations that pin the app to non-Windows OSes. Branchy products (Firefox ESR, Node) apply a start-less range to the fix's own major only. Known residual noise is NVD's own data errors (see STATUS).
25. **Install-script side effects are undone with filesystem snapshots, where the OS ships them.** On openSUSE/SLES (btrfs + snapper by default) the agent takes a snapper pre/post pair around the zypper change and rolls back with `snapper undochange pre..post`. That reverts everything the transaction did to the root filesystem, including files no package owns (proven: /etc/ld.so.cache). We didn't build our own filesystem snapshotting for ext4/xfs distros: LVM thin snapshots need free extents most hosts don't have, and a half-done snapshot layer is worse than an honest "package files and database only". After any rollback, health units that are down get restarted, because a service the bad version crashed won't come back on its own.
26. **Permanence is checked from the package, not from Windows Update's flag.** WUA's IsUninstallable said False for the very cumulative update our DISM rollback removed, so it can't gate anything. The agent downloads first, reads the top-level update.mum from the downloaded .wim (mounted read-only) or .cab, and refuses permanent or unreadable packages before installing. A servicing-stack update is the real example of a permanent package.
    Windows 11 changed the shape: one KB downloads as four packages (the cumulative update in Windows Update's "express" format, plus a servicing stack, a Safe OS update for the recovery partition and, here, an enablement package), and the express manifests ship in a `.mumx.esd` whose `collection.mumx` is an undocumented, dictionary-encoded binary format. We didn't decode it: a reverse-engineered parser behind a SYSTEM safety gate would be the riskiest code in the agent. Windows Update writes its install plan to `ActionList.xml` (plain XML) and expands the express manifests to plain files under the plan's `ExpressPackagePath` at download time, before anything is installed, so the agent reads those. Every package in the plan must have a readable update.mum. The cumulative update must not be permanent, because rollback removes only that package (removing companions would be wrong: here the enablement package is what makes the machine 26H2). Companions must be removable too, except the servicing stack (MainOS) and the Safe OS update (WinRE), which Microsoft ships as permanent with every Windows 11 cumulative update and which don't change the build rollback restores; refusing them would make every Windows 11 fix impossible. The step log names each package that stays after a rollback. Downloading the full `.msu` instead was rejected: 4.8 GB per fix, per machine.
27. **Threat model (security review round 2, 2026-10-26).** What we protect: customer hosts (the agent runs as root/SYSTEM and can change packages), the evidence record auditors rely on, tenant data, and the secrets that sign and seal them. Attackers, what they could try, and what stops them:
    - **Another tenant / internet user.** Every query is scoped by org; only owned, enrolled assets are scanned (enrolment = control of the host); signup gives you your own org only. Nothing one org claims (an external target, an unverified domain) blocks another org or reveals what it monitors. SSO starts only by POST from the sign-in page, so another site can't start a flow in a victim's browser. Alert email goes only to recipients who confirmed. Outbound requests a tenant can aim (webhooks, OIDC issuer) go through `netguard`: https only, public addresses only (incl. IPv4 hidden in IPv6 forms), redirects off, and the connection is pinned to the address that was checked, so DNS rebinding can't swap in an internal one.
    - **Non-admin user in the org (incl. anyone SSO auto-creates).** Read-only: plan/approve/auto mode, rings and health checks, enrol tokens, asset deletion, SBOM uploads and risk acceptance are admin-only on the server, and the UI disables them. Residual: no two-person approval; admins are trusted.
    - **Local unprivileged user on a managed host.** Linux state lives in root-only 0700 directories. On Windows, `ProgramData\Nimstead` is locked to SYSTEM + Administrators at enrol (before the agent key is written) and on every run: the folder is taken first (Administrators own it, explicit ACEs a user who pre-created it could have added are dropped), then listed without following junctions, and links and anything a non-admin created are deleted and reported before the agent reads anything. The enrolment token never appears on a command line. A pending Windows job is revalidated in full on load, and the SYSTEM task runs an all-users Python in isolated mode (`-I`). Proven in a VM with a standard user (sandbox/winattack.py).
    - **Compromised agent / canary host.** Its key acts only on its own asset; reports are size-capped and validated; a canary's reported versions can only pin the fleet forward (newer than installed), never to an older build.
    - **Compromised server.** It can send jobs, but the agent accepts only a closed schema: manager, package names and versions matched by strict regexes, a numeric KB, and no shell. Remediation also needs the host's local opt-in, every change is dry-run scope-checked, and rollback artefacts are hash-checked. Residual: a compromised server can still ask opted-in hosts to upgrade real packages, which is the feature itself.
    - **Insider rewriting the evidence.** Ledger entries are hash-chained, checkpoints are signed and kept off-database (in production under S3 COMPLIANCE object lock), and packs are Ed25519-signed with a pinned fingerprint. The verifier isn't shipped in the pack (whoever hands it over could swap it); it's published by the server with its SHA-256 next to the fingerprint. One key signs every tenant's packs, so each pack names the tenant's id and DNS-verified domains. Proven: a consistent rewrite is still detected.
    - **Stolen database or backup.** Passwords are argon2. SSO client secrets and webhook URLs are sealed (Vault transit in production). The dev key file is never committed (`*.key`, `*.pem` ignored).
    - **Accepted, documented residuals:** the first account on a server and dev servers with `NIMSTEAD_OPEN_SIGNUP=1` are created without proving the email address, so a squatted address there blocks that person's SSO until support moves it. Every later sign-up proves the address by an emailed link and answers the same whether or not the address has an account. Login throttling relies on the proxy passing the real client IP (`uvicorn --proxy-headers --forwarded-allow-ips`). AI calls send finding text to Anthropic when enabled. Per-user Windows apps of users who aren't logged on aren't inventoried.
28. **External scanning: only proven-owned, public hosts, and only checks we can be certain about.** The hard rule is to scan only what the customer has verified it owns, so a target needs the same per-org DNS TXT proof as SSO domains, re-checked before every scan (names change hands; a lapsed proof stops scanning and is recorded). A tenant could otherwise aim the scanner at someone else's host or at our own network, so targets must resolve to public addresses only, and connections go to the checked address. Owning a name proves nothing about the address it points at (security round 3 found a tenant could point its own verified name at a third party's IP), so the address must prove it too: the server at the exact IP about to be scanned has to serve the same per-org value at `/.well-known/nimstead-verify.txt` (HTTPS on 443 or HTTP on 80, certificate not checked: the secret in the body is the proof), checked at verification and before every scan. The cost: a host serving nothing on 80 or 443 can't be scanned. The checks are TCP connects to services that should never face the internet and a TLS handshake on 443: certain, cheap and non-intrusive (no logins, no exploits). Version fingerprinting from banners is the Tenable/Qualys noise source this product avoids; inventory-based matching through the agent stays the way to find vulnerable software. Exposed services that have no authentication by default (Redis, MongoDB, Elasticsearch, Memcached, the Docker API) score as fix-now, because exposed instances are attacked within hours.
29. **A health check is "active now and not restarted since the change", not one sample.** `systemctl is-active` is a snapshot: a service that dies and is restarted every second reads "active" for a moment each cycle, and on a real Debian 13 host that moment was what the agent saw, so a fix that broke the service was kept. The agent now records systemd's `NRestarts` for each health unit just before the change (and again before judging a rollback) and fails the check if it has gone up. It's one extra `systemctl show` per unit, needs no tuning, and catches crash loops however short the restart delay. Failures report the state ("service is activating, restarted 11 times since the change") so an admin can see why. Windows health checks are unchanged (service state only).
30. **Security review round 3 (Claude Security, 2026-10-28): 21 findings, fixed in code with a test each.** The pattern behind most of them: anyone can sign up and become an admin of their own org, so "admin" is an attacker capability for anything that crosses tenants. So nothing an org claims is globally unique until proven (external targets are per org; each org proves ownership with its own token), anything the server sends to the outside on a tenant's say-so is confirmed by the recipient (alert email) or rate-limited (manual external scans, test alerts, sign-ups), and the evidence pack names who the tenant provably is rather than what it calls itself. On Windows, the agent no longer trusts a `ProgramData\Nimstead` it didn't create: the lockdown takes ownership and resets the ACL before it lists anything, removes junctions and symlinks instead of following them, and runs before the agent key is written. Login throttling keeps a per-email cap but only applies it to addresses that have themselves failed, so a distributed attacker can't lock out the owner. Sign-up no longer says whether an email has an account: after the first account on a server, the response is the same either way and the address owner gets the next step by email (a link that creates the account, or a note that the address already has one); without SMTP, sign-up after the first account is closed (staff join by SSO) and refuses every address alike. `NIMSTEAD_OPEN_SIGNUP=1` restores instant sign-up for dev, tests and demos, logged loudly. External targets also need the per-org value served by the address being scanned (decision 28).
31. **Agents update themselves only from releases signed in CI, never by the server.** Asking people to rerun the installer on every host means outdated agents pile up, but letting the server hand out new agent code would give a compromised server root/SYSTEM on every host, which is exactly what decision 7 rules out. So a release is signed with an Ed25519 key that lives only in a protected GitHub Actions environment (owner approval, tag ruleset, passkey 2FA), with an offline backup key for rotation; both public keys are pinned in the agent. The signed manifest binds version, agent SHA-256 and commit. The server only relays it, and the agent requires a pinned key's signature over the exact bytes, a strictly newer version (an old, validly signed agent can't be pushed back), and a matching hash. It then runs the new file's `collect` on the host before swapping it in, keeps `.prev`, and never updates while a Windows job waits for its reboot or while another run holds the lock. Verification is ~60 lines of RFC 8032 in the agent (it stays stdlib-only), tested against the RFC vectors, `cryptography`, every flipped bit and non-canonical S. Rejected: plain HTTPS from GitHub (a GitHub login becomes fleet root, and many hosts can't reach it); Sigstore checked in the agent (X.509, ECDSA and transparency-log proofs hand-written in a root process). An org-wide pause and a per-host `--no-auto-update` exist; the pause is unsigned on purpose, since it can only withhold. The agent also owns its schedule now (`schedule` writes the timers or tasks; an updated agent re-applies them when `SCHEDULE_VERSION` changes), which made a 15-minute job poll possible without a reinstall: approved fixes start within minutes, and idle polls send nothing.
32. **The platform updates from signed release tags built locally, with a backup-and-restore rollback; notify by default.** Self-hosters build the image from source (decision behind `pull_policy: build`), so `deploy/update.sh` keeps that: the release manifest (same key as the agent) must be signed and its commit must equal the tag's, and it's checked by the agent from the version running now, whose keys are already trusted. Rollback restores a `pg_dump` taken just before the update into a fresh database, not Alembic downgrades: downgrades are rarely exercised on real data, and a new table left behind would break the next upgrade. The order matters for evidence (security review of this change): the image is built while the old version serves (a failed build changes nothing), the app and feeds are stopped before the dump so nothing is written after it, and feeds (which write signed checkpoints that object lock makes undeletable) only start once the new version is healthy. Otherwise a rollback would restore a ledger shorter than a checkpoint already signed, and every later evidence pack would read as tampered. Health means `/api/health` answers for the new version with the schema at its migration head. The server can't update itself (it can't rebuild its own image), so it only checks GitHub daily, alerts once per release, and fetches the signed files agents update from. Installing is opt-in (`--install-timer`) because an update runs migrations on customer data and a self-hoster should choose when.
33. **Release channels are signed, not labels.** Three channels, as most self-hosted products use: preview (earliest, may break), beta (feature-complete, being proven) and stable (public). A server follows one (`NIMSTEAD_UPDATE_CHANNEL`, default stable) and takes its channel and anything more stable. The channel is a field of the signed manifest, not a tag suffix or GitHub's pre-release flag, so neither a GitHub login nor a server can relabel a preview build as stable, and version numbers stay plain `X.Y.Z` everywhere the agent, update.sh and the workflow already parse them. A tag push signs a preview release; promotion re-signs the same commit for beta or stable through the same owner-approved environment, running from the tag (the environment only admits `v*` tags; widening it to `main` was rejected as weakening that gate). Agents need no channel: they always take exactly the release their server runs. A manifest from before channels (0.3.0) counts as preview. The release check skips releases whose manifest is missing or unsigned (one waiting for its signing approval) instead of stopping, and an explicit `update.sh --to` still has to be signed but may pick any channel.
34. **An emailed link sets the password, never the request (security round 4).** Sign-up stored the requester's password with the pending sign-up, so anyone could sign up as `victim@corp.com` with a password of their own: when the real owner clicked the genuine email's button, the attacker already held a working login to an admin account (account pre-hijacking). Now the address owner chooses the password on the link's page, a newer link replaces older ones, and the same single-use mechanism carries invitations (join an org as a member) and password resets (1 hour). A reset never signs anyone in, so it can't stand in for the authenticator code, and it ends every session.
35. **Admins can't sign in with a password alone.** An admin can change what runs as root/SYSTEM on every opted-in host, and break-glass login bypasses the IdP's MFA by design. Password admins enrol TOTP at their next sign-in and need a code (or a one-time recovery code) on every one after; members may enrol. Enrolment happens inside the login call: the server hands back a sealed, user-bound, 10-minute setup blob and creates the session only once a code proves the authenticator has the secret, so there's no half-signed-in state to police. TOTP is ~20 lines of stdlib (RFC 6238 vectors), each code works once, and wrong codes count toward the sign-in throttle and, separately, per account from every address (10 in 15 minutes, then the owner is alerted): the address throttle alone let someone holding the password spread six-digit guesses over thousands of IPv6 /64s (found by the review of this change). No admin session exists without a second factor: sign-up and its emailed link send the new admin to sign in, a promotion ends the promoted user's sessions, the 0.4.0 migration ends existing password-admin sessions, and admin routes refuse a password admin without TOTP whatever made the session. Not WebAuthn yet: it needs a library and a browser ceremony; TOTP closes the gap today and WebAuthn can be added beside it. Recovery codes are 64-bit random, so SHA-256 at rest is enough.
36. **API tokens are read-only and belong to an admin.** Scripts need findings, assets and evidence without a browser. A token reads like the admin who made it (GET only, never admin pages) and dies with that admin's role or account, so offboarding someone also ends their automations; an org-level service account would outlive the person who made it with nobody accountable. Making one needs a current authenticator code, every token expires within a year, and changing or resetting the password or signing out everywhere revokes the user's tokens too, so a stolen session can't leave a key behind that outlives the recovery. Write scopes wait for a buyer who needs them.
37. **Every tenant is bounded: body size as it's read, assets, enrolments, inventories, AI calls.** Anyone can sign up, so one org mustn't be able to load a server others share. The 10 MB body cap now counts bytes as they arrive (chunked bodies bypassed the Content-Length check), assets per org are capped, enrolments per token and inventories per org are rate-limited, and AI calls are limited per user and per org (each costs the operator money) and cached per advisory rather than per host. Users can be listed, promoted, demoted and removed, sessions idle out after 12 hours, and an org always keeps one admin. The Compose install listens on 127.0.0.1 only, because the first account created sets the server up.
38. **The first install trusts the server; we say so rather than pretend.** Updates are signed (31), but `install.sh` fetches the first agent from the server, so a compromised server can hand new hosts a modified agent (enrolled hosts are unaffected). Verifying inside the installer wouldn't help: the verifier would come from the same server. So the fetch is HTTPS-only, the installer prints the agent's SHA-256, and docs/install.md shows the out-of-band path: download the release from GitHub, check it with a trusted agent's `verify-release`, compare hashes.
39. **Agents only move forward, on their own channel.** A host records its channel at enrol (the installer passes its server's) and refuses signed releases from a less proven one, so a compromised server can't hand a stable fleet a preview build; hosts enrolled before 0.3.0 keep taking everything, as before. Remediation never installs an older build: a pinned version must be newer by the package manager's own ordering (`dpkg --compare-versions`, `apk version -t`), and any downgrade in a dry run is refused (apk would otherwise do it). Rollback copies are deleted once the outcome is saved (kept after a failed rollback), and no change starts below 1 GiB free, so neither normal use nor a stream of jobs fills the disk. A signed `min_agent_version` or revocation list was rejected: a compromised server can withhold any signal it relays, so the real defence is that hosts take the newest signed release and can never be pushed back (docs/release-keys.md).
40. **The evidence pack says what its clocks measure.** Organisations set their own remediation deadlines per priority (NIST SI-2's "organisation-defined"), shown in the pack; each finding is held to the deadline in force when it was detected, read from the ledger, so relaxing one later can't turn an old miss into a pass; Cyber Essentials' 14 days stays fixed. Mappings added for SOC 2 CC7.1 and CC8.1 (CC8.1 from the approvals actually recorded on each remediation job) and NIS2 Art. 21(2)(e). Times run from first detection, not the vendor's release date (PCI 6.3.3 asks for the latter), and the pack says so instead of implying otherwise.
41. **Confirm only what's high-stakes or hard to undo (UI round 1).** Switching the trust ladder to Auto, revoking an API token, removing someone or changing their role, signing out everywhere and cancelling a fix ask first, all through one `ConfirmDialog`; the browser's own `confirm()` is gone. Choosing a trust-ladder mode only selects it (arrow keys move through radios, so saving on change could turn on Auto by accident); Save applies it. Low-stakes per-machine settings (criticality, ring, internet-facing, health units) keep saving as you change them and say "Saved. Findings re-ranked." A per-machine edit form was rejected: more code for the same safety.
42. **One set of shared components in `web/src/ui.tsx`.** Buttons, inputs, chips, switches, tags, alerts, "Saved" messages, fields, loading states, status pills and dialogs live in one place; pages don't define their own. Admin-only actions stay focusable with `aria-disabled` and point to one visible "Read-only" note, because a disabled button with a `title` can't be reached by keyboard or touch.
43. **Square stays.** The identity is ink on paper with square corners and crimson only for "fix now" and KEV. The stray rounded chips, pills and skeletons were squared off; `rounded-full` is kept only for real circles (the switch). The remaining `rounded-*` classes do nothing under the zero-radius tokens and were left alone.
44. **The server says whether a fix is already in flight.** `/api/summary` actions carry `asset_ids` and the newest active `job`, so Home links to it instead of offering "Plan fix", which the API refuses while a job is active. Failed jobs aren't included: they're listed under "needs a look" and can be planned again.
45. **Evidence says "no activity" rather than "met" when there was nothing to assess (owner decision, 2026-10-28).** For controls that are only about timeliness (Cyber Essentials update management, NIST SI-2, CIS 7.3/7.4) a period with no fixes and nothing overdue, and for SOC 2 CC8.1 a period with no changes, is `no_activity`. An auditor reading a signed pack shouldn't have to work out that "met" meant "0 of 0". Controls that include monitoring (ISO A.8.8, RA-5, CC7.1, NIS2) or make a true negative claim (PCI 6.3.3) keep met/not met. Overdue findings always mean `not_met`. The value is added to the existing `nimstead-evidence/1` format; `verify_pack.py` doesn't read statuses, so old verifiers still verify new packs. Anyone parsing statuses should expect a third value.
46. **Onboarding asks "test or production?" with no default (owner decision, 2026-10-28).** Sandbox is fixed per machine at enrolment (carried by the token; no API changes it later). Defaulting to production meant a surprising refusal on the first fix; defaulting to test would make real machines fixable by default. Two cards, each stating its consequence, and no install command until one is chosen.
47. **TOTP setup shows a QR code drawn in the browser (owner decision, 2026-10-28).** `uqr` (MIT, no dependencies, pinned to 0.1.3) turns the `otpauth://` URI, which the browser already had, into a module matrix drawn as one SVG path: no `innerHTML`, no CSP change, and the secret never leaves the page. Always dark on white, because inverted codes fail on many phone scanners. Rejected: a server-rendered image (a new dependency in the server, and the secret sent again in an image response) and a hand-written encoder.
48. **Every dialog returns focus to what opened it (UI round 2).** Radix restores focus only to a `Dialog.Trigger`; ours open from state, so `useReturnFocus()` records the opener and refocuses it on close, for every confirmation, the palette and the drawer. The `:focus-visible` rule lives in `@layer base` so a deliberate utility wins, and headings, sections and job cards that the app focuses by script (`tabindex=-1`) show no ring. The focus colour is ink in both themes: crimson stays reserved for "fix now", KEV and errors.
49. **Feedback is announced from one place.** The shell (and the signed-out pages) hold one polite and one assertive live region; `Done` and `Notice` speak through them, because a node that appears already holding its text is often not read. `Alert` keeps `role="alert"`, which is announced as it appears. Stored states (last update failed, ledger problems, last delivery failed) are plain text, so they aren't announced on every visit.

52. **Hotpatch and cumulative fixes are separate tracks, and a Windows job may carry both KBs.** `sync_msrc` keeps the
    lowest cumulative build under the product name and the hotpatch build under `<product> (Hotpatch)` (the record still
    names the product). A host is on the hotpatch track only when its installed build *is* a known hotpatch build; then
    its CVEs with a hotpatch fix are judged by that build and the rest by cumulative builds, under one finding per CVE.
    Every other host is compared with cumulative builds, the stricter answer: a hotpatch-enrolled host on a baseline
    build looks vulnerable until it takes the month's fix, which is true. No enrolment signal is needed, which matters
    because none is documented. The plan sends the cumulative KB and, when every finding also has a hotpatch fix, the
    hotpatch KB as `alt`; the agent asks Windows Update for both and installs the one it offers (exactly one; both or
    neither = "No changes made"), then verifies against that KB's own target build.

54. **CVE List v5 is the second source for curated apps; NVD wins once it has a configuration.** NVD's enrichment
    backlog leaves recent CVEs with no CPE configuration, so the hourly update also reads the CVE List v5 delta files
    (`CVEProject/cvelistV5` releases): the vendor CNA's `affected` entries (exact vendor/product names in
    `winapps.CNA_NAMES`) and CISA's ADP "Vulnrichment" CPEs (through the same curated CPE map), with the same version
    rules as NVD (status `affected`, numeric versions, `versionType` custom/semver/dotted only; unbounded or `*` ends,
    `git` versions and unknown status are refused). Google's CNA writes `version == lessThan` to mean "below X"; that is
    read as a range from the beginning. Rows are `<CVE>-v5` (CVE as alias), only for CVEs with no NVD row, and NVD's
    sync deletes them when it configures the CVE. The first run takes only the newest delta: history stays NVD's.
    End of life for curated apps comes from endoflife.date cycles (Node.js, Python, Oracle JDK), schema-checked, last
    good cycles kept; Microsoft's own dates stay in the dated table (plan decision 5).

56. **Fixes obey time and topology (plan T13, T14, T40–T43, decision 12).** An approved job is handed out only inside
    its machine's maintenance window, or the org's (none = any time, as before); a window lasts its hours of real time,
    also across a clock change. Hosts in one failover cluster (`HKLM\Cluster`), or one domain's controllers, form a
    group with one Windows job in flight; a cluster node is drained (`Suspend-ClusterNode -Drain`) before the install,
    a failed drain changes nothing, and the node is resumed after success, rollback or a failed start. Restarts:
    servers restart at once (they're inside their window); a workstation with someone signed in is told and may put it
    off until the job's `reboot_by` (dispatch + the org's deadline, default 24 h), reminded at most hourly, then gets a
    15-minute warning; a job whose restart was put off isn't judged until it has happened. The server's silence timeout for a
    Windows job is therefore the restart deadline plus 4 hours, not 2 hours (a Windows host that dies is flagged later). No install starts on battery
    below half, or with under 10 GB free on the system drive (a 40 GB Windows 11 VM filled up after one install and
    rollback, WinSxS 19.6 GB, and the next download failed with a bare code 4; refusing first says why and changes
    nothing). Health checks also fail on Service Control Manager crash/stop events for the unit since the change.
    When Windows Update offers nothing, the step says why from the machine's own settings (WSUS approval, deferral or
    pause policy, no ESU licence). Unmanaged hosts: an opted-in domain member reads enabled computer objects using only
    its own computer account (`[adsisearcher]`), and Assets lists those signed in within 30 days with no agent, with end
    of support from their AD OS string. Not built: downloading updates before the window opens (installs still happen
    only inside it) and detecting metered connections.
57. **App, Office and setting fixes: closed maps in the agent, forward-only fixes only by a person (plan T16, T17, T21,
    T22, T38).** Three managers beside `windows`: `winget` (curated apps, Edge, VS Code), `office` (Click-to-Run) and
    `winconfig` (six settings). The agent holds the maps (`WINGET_IDS`: product key -> winget id; `CONFIG_FIXES`:
    check id -> registry value); a job names only a key and versions, so a compromised server can at most move a curated
    app to a newer published build or apply one of those exact settings. winget runs only from the App Installer folder
    under the TrustedInstaller-owned WindowsApps root, itself owned by TrustedInstaller, SYSTEM or Administrators (by SID;
    a real Windows 11 26H2 has it owned by Administrators, so "TrustedInstaller only" never found winget; as SYSTEM it is run from the VCLibs folder, under the same ownership rule, or it exits with a missing-DLL error), with `--source winget --exact --id`, a version newer than installed, and only when
    `winget show` lists an installer SHA-256 for it; it is **forward-only**: the job says so, approving needs the
    approver's explicit acknowledgement (recorded in the ledger), and neither the trust ladder nor auto mode ever plans or
    approves it. Office updates to the planned build with `OfficeC2RClient.exe updatetoversion=`, refuses while any Office
    app is open (never force-closes), and rolls back to the build it found. A setting change records the value (or its
    absence) first and puts exactly that back on failure; setting fixes are manual-only too, because SMB signing or
    NTLMv1 changes can break old clients. Dropped: .NET Framework updates (T16), because .NET Framework isn't detected
    (DECISIONS 51). Blocked on the owner: the hotpatch VM proof (T15, needs an Azure subscription).

59. **Findings that have no fixed version but do have a fix count as fixable (2026-10-31).** The UI review of a seeded Windows fleet opened on "Nothing matches": Fixable only is on by default and meant "has a fixed version", which settings, end of support and exposures never have, so three Fix now findings were hidden. The default stays, because hiding CVEs nobody can patch yet is still right; the filter now counts those three kinds as fixable, and they read "change the setting", "move to a supported version" or "close or restrict it" instead of "no fix yet". The finding page also offers Plan fix for the settings the agent can change: the API accepted those jobs, but nothing in the UI could start one. A CVE fixed by a setting (CVE-2013-3900) is no longer scored down as having no fix, so its score rises.
60. **The restart notice doesn't promise Windows will wait (2026-10-31).** On a signed-in Windows 11 VM the agent put its restart off as designed, then Windows Update's own TrustedInstaller restarted at 59 minutes, before the 1-hour deadline, at 04:44 guest time. The earlier unexplained 45-minute restart was probably the same, though it wasn't captured. Holding it back would mean changing the host's Windows Update policy, and restoring it, for a promise only the agent's own restart needs, so the notice says Windows may restart sooner. The VM test now fails only if the agent restarts early.
61. **.NET SDKs are matched by feature band (2026-11-01).** Comparing Microsoft's findings with its .NET release data showed SDK-only fixes nobody saw, such as 8.0.427: they were dropped so they could never be compared with a runtime. Each band (8.0.1xx, 8.0.4xx) is patched on its own line, so the agent reports the newest of each and a fix applies to its own band only. A fix Microsoft publishes for one band can apply to another without our saying so: a possible miss, which we take over a guess (DECISIONS 4). SDKs get no end-of-support finding of their own, because the runtime beside them already has one.
62. **A VM harness resets a VM only when its disk has gone idle (2026-10-31).** The fixed 12-minute reset killed Windows setup still working on a slow boot ("The computer restarted unexpectedly"), so runs passed only when setup was fast and failures looked random. A hard reset of a booted Windows lost its unflushed writes too, so one that has booted but whose guest control never came up gets a clean restart instead. Why guest control sometimes stays down until a cold boot is still unknown.
