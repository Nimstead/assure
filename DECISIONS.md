# Key decisions

Short log; newest last. Why, not what.

1. **Inventory-based detection over network banner scanning.** An agent reports installed packages; matching happens server-side against OSV. Banner/version guessing is the main source of Tenable/Qualys noise. Network scanning may come later, gated on verified ownership.
2. **OSV.dev as primary advisory source.** One schema covering Debian, Ubuntu, Alpine, RHEL-family, SUSE, PyPI, npm, Go, crates etc., with distro-native fixed versions (backport-aware). Mirrored locally (bulk zips) so detection is fast, offline and auto-updating.
3. **Match distro packages by source package name**, which is what distro advisories reference. Agent must report source names (dpkg `${source:Package}`, rpm SOURCERPM, apk origin).
4. **Refuse to guess.** Unknown ecosystem or unparseable version → no finding (and later a data-quality metric), never a fuzzy match.
5. **Accuracy is tested against OSV itself.** `tests/fetch_fixtures.py` stores real OSV records plus OSV API answers; tests require exact agreement.
6. **Stack:** Python 3.14 + FastAPI 0.162 + SQLAlchemy 2.1 + Pydantic 2.14 (uv). SQLite in dev/tests, Postgres in prod. React + Vite + TS SPA for the UI (logged-in app, no SEO need → no SSR framework).
7. **Remediation never runs shell from the server.** Jobs are closed descriptions (manager + validated package names/versions); the agent maps them to fixed argv templates. A compromised server can't turn the fleet into RCE beyond "upgrade these packages", and only on hosts that opted in locally (`enroll --allow-remediation`).
8. **Reversible or not at all.** The agent saves a rollback package (apt/apk cache or download, sha256 recorded) for every package before changing anything, and aborts if it can't. Health checks (systemd units) run before and after; failure → automatic rollback → verify versions restored. Rollback failure is reported as `rollback_failed`, never swallowed.
9. **Success = proof, not a claim.** A job is `succeeded` only when the next inventory shows its findings resolved; otherwise `not_fixed`.
10. **Trust ladder + canaries.** Org mode suggest → approve → auto. Auto changes land on ring-0 canaries first; the broad ring waits for a canary success that has soaked N hours, and any failure of that change anywhere halts rollout.
11. **Dev guard:** until `NIMSTEAD_ALLOW_PRODUCTION_REMEDIATION=1`, jobs only go to assets enrolled with a sandbox token.
12. **Evidence = hash-chained ledger + Ed25519-signed packs** verifiable offline with a shipped script; the server refuses to sign if the chain fails verification. Time-to-remediate is measured from first detection to the first inventory proving the fix (stated in each pack).
13. **Security review (Opus) round 1 fixed:** pinned signing-key fingerprint for offline verification; stale-job sweep + late reports accepted; outcomes persisted on the agent before reporting; rollback artefacts copied into our own dir and hash-checked before use; dry-run refuses transactions touching unplanned packages; `--no-remove`; kill switch and canary re-checked at dispatch; broad ring pinned to canary-proven versions; enrol tokens expire (30 d) and revoke; asset delete; Origin check, 10 MB body cap, timing-safe login, no-redirect agent HTTP. dnf removed until proven in a sandbox.
14. **Known ledger limit:** a DB-level attacker can still rewrite or truncate the whole chain and have the server sign it. Mitigations now: lifecycle timings come from the ledger (not the mutable findings table), and every pack carries `chain_head` so successive packs expose a rewritten history. Next: periodically signed checkpoints stored off-database / RFC 3161 timestamps.
15. **Remediation is apt-only for now.** The first real-host run (Debian 13 WSL sandbox) showed installed versions are usually superseded in the archive and absent from the cache, so no pristine rollback copy exists. For apt the agent now rebuilds the installed package from its files + dpkg metadata (native dpkg-repack via `dpkg-deb`), capturing the exact prior state; proven in the sandbox (upgrade verified by inventory; forced service failure rolled back with versions restored). Alpine has no equivalent we trust yet (no historic archive, apk v2/v3 format split) and dnf is unproven, so both are detection-only and the server refuses to plan them.
16. **apk and dnf rollback = snapshot.** Neither ecosystem keeps old builds, so before a change the agent archives every file the planned packages own plus the package database (`/lib/apk/db` + `/etc/apk/world`, or `/var/lib/rpm`), sha256-recorded. Rollback removes files the new version added, restores the archive and the database, and verifies versions. This is only sound because the dry run proves the transaction touches nothing outside the plan (on Alpine it correctly refused openssl/zlib fixes that also needed musl). `apk add` would also pin packages into the world file, so the world file is restored after every apply. Proven on Alpine 3.21 (injected failure) and AlmaLinux 9 (real service failure) in disposable VMs.
17. **Windows: OS detection via MSRC, no remediation, no third-party apps (yet).** The OS build is matched against MSRC FixedBuild per product: exact and low-noise. Third-party Windows apps have no reliable advisory source keyed by what's installed (CPE matching is the noisy Tenable/Qualys approach we reject). Windows remediation can't be tested here: Windows Home has no Hyper-V or Windows Sandbox, so a disposable Windows VM needs a hypervisor and an image only the user can provide. Per the hard rule (test only in sandboxes), it isn't built.
18. **SSO needs proof of domain ownership.** An org's SSO only routes emails on domains verified by a DNS TXT record (`_nimstead-verify.<domain>`, an HMAC of org + domain under the server key, so nothing extra is stored). Unverified claims can't block the real owner, and a domain verified by one org can't be taken by another. The client secret is Fernet-encrypted at rest; plaintext is refused, never used silently. "Require SSO" keeps password access for admins only, as a recorded and alerted break-glass, so a broken IdP can't lock an org out.
19. **State that must hold across API workers lives in the DB:** failed-login throttle, per-asset inventory rate limit, and SSO pending logins (single use, expiring). No in-process dictionaries remain.
20. **Dependencies join the plan explicitly.** When the dry run refuses a fix because it needs other packages (e.g. openssl → musl), the user can re-plan "including musl". The dependencies are then snapshotted, rolled back and verified with the fix. Nothing is expanded silently.
21. **Application dependencies come in as CycloneDX SBOMs** (purl → OSV ecosystem), kept separate from agent OS inventory so neither upload wipes the other. Maven, NuGet and RubyGems comparators meet the same bar as the distro ones: exact agreement with the OSV API on real packages (log4j-core, jackson-databind, Newtonsoft.Json, rack, nokogiri…).
