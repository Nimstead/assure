# Key decisions

Short log; newest last. Why, not what.

1. **Inventory-based detection over network banner scanning.** An agent reports installed packages; matching happens server-side against OSV. Banner/version guessing is the main source of commercial-scanner noise. Network scanning may come later, gated on verified ownership.
2. **OSV.dev as primary advisory source.** One schema covering Debian, Ubuntu, Alpine, RHEL-family, SUSE, PyPI, npm, Go, crates etc., with distro-native fixed versions (backport-aware). Mirrored locally (bulk zips) so detection is fast, offline and auto-updating.
3. **Match distro packages by source package name**, which is what distro advisories reference. Agent must report source names (dpkg `${source:Package}`, rpm SOURCERPM, apk origin).
4. **Refuse to guess.** Unknown ecosystem or unparseable version → no finding (and later a data-quality metric), never a fuzzy match.
5. **Accuracy is tested against OSV itself.** `tests/fetch_fixtures.py` stores real OSV records plus OSV API answers; tests require exact agreement.
6. **Stack:** Python 3.14 + FastAPI 0.162 + SQLAlchemy 2.1 + Pydantic 2.14 (uv). SQLite in dev/tests, Postgres in prod. React + Vite + TS SPA for the UI (logged-in app, no SEO need → no SSR framework).
7. **Remediation never runs shell from the server.** Jobs are closed descriptions (manager + validated package names/versions); the agent maps them to fixed argv templates. A compromised server can't turn the fleet into RCE beyond "upgrade these packages", and only on hosts that opted in locally (`enroll --allow-remediation`). Since DECISIONS 129, a host opted in locally to network checks (`enroll --allow-network-checks`) also connects to devices in its own neighbour table on its own private subnets with the signed agent's fixed read-only checks, chosen by the agent, and nothing else.
8. **Reversible or not at all.** The agent saves a rollback package (apt/apk cache or download, sha256 recorded) for every package before changing anything, and aborts if it can't. Health checks (systemd units) run before and after; failure → automatic rollback → verify versions restored. Rollback failure is reported as `rollback_failed`, never swallowed.
9. **Success = proof, not a claim.** A job is `succeeded` only when the next inventory shows its findings resolved; otherwise `not_fixed`.
10. **Trust ladder + canaries.** Org mode suggest → approve → auto. Auto changes land on ring-0 canaries first; the broad ring waits for a canary success that has soaked N hours, and any failure of that change anywhere halts rollout.
11. **Dev guard:** until `NIMSTEAD_ALLOW_PRODUCTION_REMEDIATION=1`, jobs only go to assets enrolled with a sandbox token.
12. **Evidence = hash-chained ledger + Ed25519-signed packs** verifiable offline with a shipped script; the server refuses to sign if the chain fails verification. Time-to-remediate is measured from first detection to the first inventory proving the fix (stated in each pack).
13. **Security review (Opus) round 1 fixed** ("dnf removed" below is superseded by 16)**:** pinned signing-key fingerprint for offline verification; stale-job sweep + late reports accepted; outcomes persisted on the agent before reporting; rollback artefacts copied into our own dir and hash-checked before use; dry-run refuses transactions touching unplanned packages; `--no-remove`; kill switch and canary re-checked at dispatch; broad ring pinned to canary-proven versions; enrol tokens expire (30 d) and revoke; asset delete; Origin check, 10 MB body cap, timing-safe login, no-redirect agent HTTP. dnf removed until proven in a sandbox.
14. **Known ledger limit:** a DB-level attacker can still rewrite or truncate the whole chain and have the server sign it. Mitigations now: lifecycle timings come from the ledger (not the mutable findings table), and every pack carries `chain_head` so successive packs expose a rewritten history. Next: periodically signed checkpoints stored off-database / RFC 3161 timestamps.
15. **Remediation is apt-only for now** (superseded: apk and dnf by 16, zypper by 25)**.** The first real-host run (Debian 13 WSL sandbox) showed installed versions are usually superseded in the archive and absent from the cache, so no pristine rollback copy exists. For apt the agent now rebuilds the installed package from its files + dpkg metadata (native dpkg-repack via `dpkg-deb`), capturing the exact prior state; proven in the sandbox (upgrade verified by inventory; forced service failure rolled back with versions restored). Alpine has no equivalent we trust yet (no historic archive, apk v2/v3 format split) and dnf is unproven, so both are detection-only and the server refuses to plan them.
16. **apk and dnf rollback = snapshot.** Neither ecosystem keeps old builds, so before a change the agent archives every file the planned packages own plus the package database (`/lib/apk/db` + `/etc/apk/world`, or `/var/lib/rpm`), sha256-recorded. Rollback removes files the new version added, restores the archive and the database, and verifies versions. This is only sound because the dry run proves the transaction touches nothing outside the plan (on Alpine it correctly refused openssl/zlib fixes that also needed musl). `apk add` would also pin packages into the world file, so the world file is restored after every apply. Proven on Alpine 3.21 (injected failure) and AlmaLinux 9 (real service failure) in disposable VMs.
17. **Windows: OS detection via MSRC, no remediation; third-party apps: see 22** (remediation superseded by 22: one cumulative update, reversible by DISM)**.** The OS build is matched against MSRC FixedBuild per product: exact and low-noise. Third-party Windows apps have no reliable advisory source keyed by what's installed (CPE matching is the noisy commercial-scanner approach we reject). Windows remediation can't be tested here: Windows Home has no Hyper-V or Windows Sandbox, so a disposable Windows VM needs a hypervisor and an image only the user can provide. Per the hard rule (test only in sandboxes), it isn't built.
18. **SSO needs proof of domain ownership.** An org's SSO only routes emails on domains verified by a DNS TXT record (`_nimstead-verify.<domain>`, an HMAC of org + domain under the server key, so nothing extra is stored). Unverified claims can't block the real owner, and a domain verified by one org can't be taken by another. The client secret is Fernet-encrypted at rest; plaintext is refused, never used silently. "Require SSO" keeps password access for admins only, as a recorded and alerted break-glass, so a broken IdP can't lock an org out.
19. **State that must hold across API workers lives in the DB:** failed-login throttle, per-asset inventory rate limit, and SSO pending logins (single use, expiring). No in-process dictionaries remain.
20. **Dependencies join the plan explicitly.** When the dry run refuses a fix because it needs other packages (e.g. openssl → musl), the user can re-plan "including musl". The dependencies are then snapshotted, rolled back and verified with the fix. Nothing is expanded silently.
21. **Application dependencies come in as CycloneDX SBOMs** (purl → OSV ecosystem), kept separate from agent OS inventory so neither upload wipes the other. Maven, NuGet and RubyGems comparators meet the same bar as the distro ones: exact agreement with the OSV API on real packages (log4j-core, jackson-databind, Newtonsoft.Json, rack, nokogiri…).
22. **Windows remediation = one cumulative update, reversible by DISM.** The agent installs exactly the KB that reaches the highest fixed build, via the Windows Update Agent as SYSTEM; Windows Update must offer exactly that update first. The job is a state machine persisted across reboots (install → reboot → verify build + health → done, or remove the newly added RollupFix package with DISM → reboot → verify the original build). DISM's transient "servicing busy" errors right after boot are retried (seen for real: 0x80010108). A permanent package or a build that doesn't return is `rollback_failed`, loud. Proven on Windows Server 2025 in a disposable VirtualBox VM (`sandbox/winvm.py`, `wine2e.py`). Gotchas found there: VirtualBox 7 NAT blocks guest→host localhost unless `--nat-localhostreachable1 on`; guest control mangles quoting (use `-EncodedCommand`); unattended setup reboots hang under Hyper-V's NEM backend (auto-reset).
23. **Production keys live in Vault, checkpoints in object-locked S3.** Vault transit signs evidence (Ed25519, so offline verification is unchanged), encrypts SSO secrets and HMACs domain tokens; the key never leaves Vault and failures are loud (no silent fallback to local keys). Checkpoints are written with COMPLIANCE-mode object lock, so even the bucket owner can't delete or shorten them. Proven against real Vault and an S3 gateway (MinIO OSS is archived; Versity's S3 gateway was used).
24. **Windows third-party apps: a curated CPE map, never fuzzy matching.** `winapps.py` maps ~18 widely deployed apps from a strict full-match on the registry DisplayName (plus Publisher where the name is generic, e.g. "Git", "Python", "Zoom") to an exact NVD `vendor:product`, with a per-product version normaliser. NVD's CPE match data for only those CPEs becomes OSV-shaped `WinApp` advisories (ranges translated as introduced/fixed/last_affected); an app not in the map is inventory and is never compared. Why not match any DisplayName against all CPEs: that is the commercial-scanner noise this product exists to avoid (name collisions like "Chrome Remote Desktop", wrong editions, vendor-name drift). Dropped on purpose, not approximated: Java 8 (registry 8.0.4310.10 vs NVD "1.8.0 update431"), Eclipse Temurin (no CPE exists), matches with no end bound, exclusive start bounds, pre-release/non-numeric versions, mobile/macOS/Linux targets, classic-track Acrobat, AND-configurations that pin the app to non-Windows OSes. Branchy products (Firefox ESR, Node) apply a start-less range to the fix's own major only. Known residual noise is NVD's own data errors (see STATUS).
25. **Install-script side effects are undone with filesystem snapshots, where the OS ships them.** On openSUSE/SLES (btrfs + snapper by default) the agent takes a snapper pre/post pair around the zypper change and rolls back with `snapper undochange pre..post`. That reverts everything the transaction did to the root filesystem, including files no package owns (proven: /etc/ld.so.cache). We didn't build our own filesystem snapshotting for ext4/xfs distros: LVM thin snapshots need free extents most hosts don't have, and a half-done snapshot layer is worse than an honest "package files and database only". After any rollback, health units that are down get restarted, because a service the bad version crashed won't come back on its own.
26. **Permanence is checked from the package, not from Windows Update's flag.** WUA's IsUninstallable said False for the very cumulative update our DISM rollback removed, so it can't gate anything. The agent downloads first, reads the top-level update.mum from the downloaded .wim (mounted read-only) or .cab, and refuses permanent or unreadable packages before installing. A servicing-stack update is the real example of a permanent package.
    Windows 11 changed the shape: one KB downloads as four packages (the cumulative update in Windows Update's "express" format, plus a servicing stack, a Safe OS update for the recovery partition and, here, an enablement package), and the express manifests ship in a `.mumx.esd` whose `collection.mumx` is an undocumented, dictionary-encoded binary format. We didn't decode it: a reverse-engineered parser behind a SYSTEM safety gate would be the riskiest code in the agent. Windows Update writes its install plan to `ActionList.xml` (plain XML) and expands the express manifests to plain files under the plan's `ExpressPackagePath` at download time, before anything is installed, so the agent reads those. Every package in the plan must have a readable update.mum. The cumulative update must not be permanent, because rollback removes only that package (removing companions would be wrong: here the enablement package is what makes the machine 26H2). Companions must be removable too, except the servicing stack (MainOS) and the Safe OS update (WinRE), which Microsoft ships as permanent with every Windows 11 cumulative update and which don't change the build rollback restores; refusing them would make every Windows 11 fix impossible. The step log names each package that stays after a rollback. Downloading the full `.msu` instead was rejected: 4.8 GB per fix, per machine.
27. **Threat model (security review round 2, 2026-10-26).** What we protect: customer hosts (the agent runs as root/SYSTEM and can change packages), the evidence record auditors rely on, tenant data, and the secrets that sign and seal them. Attackers, what they could try, and what stops them:
    - **Another tenant / internet user.** Every query is scoped by org; only owned, enrolled assets are scanned (enrolment = control of the host); signup gives you your own org only. Nothing one org claims (an external target, an unverified domain) blocks another org or reveals what it monitors. SSO starts only by POST from the sign-in page, so another site can't start a flow in a victim's browser. Alert email goes only to recipients who confirmed. Outbound requests a tenant can aim (webhooks, OIDC issuer) go through `netguard`: https only, public addresses only (incl. IPv4 hidden in IPv6 forms), redirects off, and the connection is pinned to the address that was checked, so DNS rebinding can't swap in an internal one.
    - **Non-admin user in the org (incl. anyone SSO auto-creates).** Read-only: plan/approve/auto mode, rings and health checks, enrol tokens, asset deletion, SBOM uploads and risk acceptance are admin-only on the server, and the UI disables them. Residual: no two-person approval; admins are trusted.
    - **Local unprivileged user on a managed host.** Linux state lives in root-only 0700 directories. On Windows, `ProgramData\Nimstead` is locked to SYSTEM + Administrators at enrol (before the agent key is written) and on every run: the folder is taken first (Administrators own it, explicit ACEs a user who pre-created it could have added are dropped), then listed without following junctions, and links and anything a non-admin created are deleted and reported before the agent reads anything. The enrolment token never appears on a command line. A pending Windows job is revalidated in full on load, and the SYSTEM task runs an all-users Python in isolated mode (`-I`). Proven in a VM with a standard user (sandbox/winattack.py).
    - **Compromised agent / canary host.** Its key acts only on its own asset; reports are size-capped and validated; a canary's reported versions can only pin the fleet forward (newer than installed), never to an older build.
    - **Compromised server.** It can send jobs, but the agent accepts only a closed schema: manager, package names and versions matched by strict regexes, a numeric KB, and no shell. Remediation also needs the host's local opt-in, every change is dry-run scope-checked, and rollback artefacts are hash-checked. Residual: a compromised server can still ask opted-in hosts to upgrade real packages, which is the feature itself.
    - **Insider rewriting the evidence.** Ledger entries are hash-chained, checkpoints are signed and kept off-database (in production under S3 COMPLIANCE object lock), and packs are Ed25519-signed with a pinned fingerprint. The verifier isn't shipped in the pack (whoever hands it over could swap it); it's published by the server with its SHA-256 next to the fingerprint. One key signs every tenant's packs, so each pack names the tenant's id and DNS-verified domains. Proven: a consistent rewrite is still detected.
    - **Stolen database or backup.** Passwords are argon2. SSO client secrets and webhook URLs are sealed (Vault transit in production). The dev key file is never committed (`*.key`, `*.pem` ignored).
    - **Accepted, documented residuals:** the first account on a server and dev servers with `NIMSTEAD_OPEN_SIGNUP=1` are created without proving the email address, so a squatted address there blocks that person's SSO until support moves it. Every later sign-up proves the address by an emailed link and answers the same whether or not the address has an account. Login throttling relies on the proxy passing the real client IP (`uvicorn --proxy-headers --forwarded-allow-ips`). AI calls send finding text to Anthropic when enabled. Per-user Windows apps of users who aren't logged on aren't inventoried.
28. **External scanning: only proven-owned, public hosts, and only checks we can be certain about.** The hard rule is to scan only what the customer has verified it owns, so a target needs the same per-org DNS TXT proof as SSO domains, re-checked before every scan (names change hands; a lapsed proof stops scanning and is recorded). A tenant could otherwise aim the scanner at someone else's host or at our own network, so targets must resolve to public addresses only, and connections go to the checked address. Owning a name proves nothing about the address it points at (security round 3 found a tenant could point its own verified name at a third party's IP), so the address must prove it too: the server at the exact IP about to be scanned has to serve the same per-org value at `/.well-known/nimstead-verify.txt` (HTTPS on 443 or HTTP on 80, certificate not checked: the secret in the body is the proof), checked at verification and before every scan. The cost: a host serving nothing on 80 or 443 can't be scanned. The checks are TCP connects to services that should never face the internet and a TLS handshake on 443: certain, cheap and non-intrusive (no logins, no exploits). Version fingerprinting from banners is the commercial-scanner noise source this product avoids; inventory-based matching through the agent stays the way to find vulnerable software. Exposed services that have no authentication by default (Redis, MongoDB, Elasticsearch, Memcached, the Docker API) score as fix-now, because exposed instances are attacked within hours.
29. **A health check is "active now and not restarted since the change", not one sample.** `systemctl is-active` is a snapshot: a service that dies and is restarted every second reads "active" for a moment each cycle, and on a real Debian 13 host that moment was what the agent saw, so a fix that broke the service was kept. The agent now records systemd's `NRestarts` for each health unit just before the change (and again before judging a rollback) and fails the check if it has gone up. It's one extra `systemctl show` per unit, needs no tuning, and catches crash loops however short the restart delay. Failures report the state ("service is activating, restarted 11 times since the change") so an admin can see why. Windows health checks are unchanged (service state only).
30. **Security review round 3 (Claude Security, 2026-10-28): 21 findings, fixed in code with a test each.** The pattern behind most of them: anyone can sign up and become an admin of their own org, so "admin" is an attacker capability for anything that crosses tenants. So nothing an org claims is globally unique until proven (external targets are per org; each org proves ownership with its own token), anything the server sends to the outside on a tenant's say-so is confirmed by the recipient (alert email) or rate-limited (manual external scans, test alerts, sign-ups), and the evidence pack names who the tenant provably is rather than what it calls itself. On Windows, the agent no longer trusts a `ProgramData\Nimstead` it didn't create: the lockdown takes ownership and resets the ACL before it lists anything, removes junctions and symlinks instead of following them, and runs before the agent key is written. Login throttling keeps a per-email cap but only applies it to addresses that have themselves failed, so a distributed attacker can't lock out the owner. Sign-up no longer says whether an email has an account: after the first account on a server, the response is the same either way and the address owner gets the next step by email (a link that creates the account, or a note that the address already has one); without SMTP, sign-up after the first account is closed (staff join by SSO) and refuses every address alike. `NIMSTEAD_OPEN_SIGNUP=1` restores instant sign-up for dev, tests and demos, logged loudly. External targets also need the per-org value served by the address being scanned (decision 28).
31. **Agents update themselves only from releases signed in CI, never by the server.** Asking people to rerun the installer on every host means outdated agents pile up, but letting the server hand out new agent code would give a compromised server root/SYSTEM on every host, which is exactly what decision 7 rules out. So a release is signed with an Ed25519 key that lives only in a protected GitHub Actions environment (owner approval, tag ruleset, passkey 2FA), with an offline backup key for rotation; both public keys are pinned in the agent. The signed manifest binds version, agent SHA-256 and commit. The server only relays it, and the agent requires a pinned key's signature over the exact bytes, a strictly newer version (an old, validly signed agent can't be pushed back), and a matching hash. It then runs the new file's `collect` on the host before swapping it in, keeps `.prev`, and never updates while a Windows job waits for its reboot or while another run holds the lock. Verification is ~60 lines of RFC 8032 in the agent (it stays stdlib-only), tested against the RFC vectors, `cryptography`, every flipped bit and non-canonical S. Rejected: plain HTTPS from GitHub (a GitHub login becomes fleet root, and many hosts can't reach it); Sigstore checked in the agent (X.509, ECDSA and transparency-log proofs hand-written in a root process). An org-wide pause and a per-host `--no-auto-update` exist; the pause is unsigned on purpose, since it can only withhold. The agent also owns its schedule now (`schedule` writes the timers or tasks; an updated agent re-applies them when `SCHEDULE_VERSION` changes), which made a 15-minute job poll possible without a reinstall: approved fixes start within minutes, and idle polls send nothing.
32. **The platform updates from signed release tags built locally, with a backup-and-restore rollback; notify by default.** Self-hosters build the image from source (decision behind `pull_policy: build`), so `deploy/update.sh` keeps that: the release manifest (same key as the agent) must be signed and its commit must equal the tag's, and it's checked by the agent from the version running now, whose keys are already trusted. Rollback restores a `pg_dump` taken just before the update into a fresh database, not Alembic downgrades: downgrades are rarely exercised on real data, and a new table left behind would break the next upgrade. The order matters for evidence (security review of this change): the image is built while the old version serves (a failed build changes nothing), the app and feeds are stopped before the dump so nothing is written after it, and feeds (which write signed checkpoints that object lock makes undeletable) only start once the new version is healthy. Otherwise a rollback would restore a ledger shorter than a checkpoint already signed, and every later evidence pack would read as tampered. Health means `/api/health` answers for the new version with the schema at its migration head. The server can't update itself (it can't rebuild its own image), so it only checks GitHub daily, alerts once per release, and fetches the signed files agents update from. Installing is opt-in (`--install-timer`) because an update runs migrations on customer data and a self-hoster should choose when.
33. **Release channels are signed, not labels.** Three channels, as most self-hosted products use: preview (earliest, may break), beta (feature-complete, being proven) and stable (public). A server follows one (`NIMSTEAD_UPDATE_CHANNEL`, default stable) and takes its channel and anything more stable. The channel is a field of the signed manifest, not a tag suffix or GitHub's pre-release flag, so neither a GitHub login nor a server can relabel a preview build as stable, and version numbers stay plain `X.Y.Z` everywhere the agent, update.sh and the workflow already parse them. A tag push signs a preview release; promotion re-signs the same commit for beta or stable through the same owner-approved environment, running from the tag (the environment only admits `v*` tags; widening it to `main` was rejected as weakening that gate). Agents need no channel: they always take exactly the release their server runs. A manifest from before channels (0.3.0) counts as preview. The release check skips releases whose manifest is missing or unsigned (one waiting for its signing approval) instead of stopping, and an explicit `update.sh --to` still has to be signed but may pick any channel.
34. **An emailed link sets the password, never the request (security round 4).** Sign-up stored the requester's password with the pending sign-up, so anyone could sign up as `victim@corp.com` with a password of their own: when the real owner clicked the genuine email's button, the attacker already held a working login to an admin account (account pre-hijacking). Now the address owner chooses the password on the link's page, a newer link replaces older ones, and the same single-use mechanism carries invitations (join an org as a member) and password resets (1 hour). A reset never signs anyone in, so it can't stand in for the authenticator code, and it ends every session.
35. **Admins can't sign in with a password alone.** An admin can change what runs as root/SYSTEM on every opted-in host, and break-glass login bypasses the IdP's MFA by design. Password admins enrol TOTP at their next sign-in and need a code (or a one-time recovery code) on every one after; members may enrol. Enrolment happens inside the login call: the server hands back a sealed, user-bound, 10-minute setup blob and creates the session only once a code proves the authenticator has the secret, so there's no half-signed-in state to police. TOTP is ~20 lines of stdlib (RFC 6238 vectors), each code works once, and wrong codes count toward the sign-in throttle and, separately, per account from every address (10 in 15 minutes, then the owner is alerted): the address throttle alone let someone holding the password spread six-digit guesses over thousands of IPv6 /64s (found by the review of this change). No admin session exists without a second factor: sign-up and its emailed link send the new admin to sign in, a promotion ends the promoted user's sessions, the 0.4.0 migration ends existing password-admin sessions, and admin routes refuse a password admin without TOTP whatever made the session. Not WebAuthn yet: it needs a library and a browser ceremony; TOTP closes the gap today and WebAuthn can be added beside it. Recovery codes are 64-bit random, so SHA-256 at rest is enough.
36. **API tokens are read-only and belong to an admin.** Scripts need findings, assets and evidence without a browser. A token reads like the admin who made it (GET only, never admin pages) and dies with that admin's role or account, so offboarding someone also ends their automations; an org-level service account would outlive the person who made it with nobody accountable. Making one needs a current authenticator code, every token expires within a year, and changing or resetting the password or signing out everywhere revokes the user's tokens too, so a stolen session can't leave a key behind that outlives the recovery. Write scopes wait for a buyer who needs them.
37. **Every tenant is bounded: body size as it's read, assets, enrolments, inventories, AI calls.** Anyone can sign up, so one org mustn't be able to load a server others share. The 10 MB body cap now counts bytes as they arrive (chunked bodies bypassed the Content-Length check), assets per org are capped, enrolments per token and inventories per org are rate-limited, and AI calls are limited per user and per org (each costs the operator money) and cached per advisory rather than per host. Users can be listed, promoted, demoted and removed, sessions idle out after 12 hours, and an org always keeps one admin. The Compose install listens on 127.0.0.1 only, because the first account created sets the server up.
38. **The first install trusts the server; we say so rather than pretend.** Updates are signed (31), but `install.sh` fetches the first agent from the server, so a compromised server can hand new hosts a modified agent (enrolled hosts are unaffected). Verifying inside the installer wouldn't help: the verifier would come from the same server. So the fetch is HTTPS-only, the installer prints the agent's SHA-256, and docs/install.md shows the out-of-band path: download the release from GitHub, check it with a trusted agent's `verify-release`, compare hashes.
39. **Agents only move forward, on their own channel.** A host records its channel at enrol (the installer passes its server's) and refuses signed releases from a less proven one, so a compromised server can't hand a stable fleet a preview build; hosts enrolled before 0.3.0 keep taking everything, as before. Remediation never installs an older build: a pinned version must be newer by the package manager's own ordering (`dpkg --compare-versions`, `apk version -t`), and any downgrade in a dry run is refused (apk would otherwise do it). Rollback copies are deleted once the outcome is saved (kept after a failed rollback), and no change starts below 1 GiB free, so neither normal use nor a stream of jobs fills the disk. A signed `min_agent_version` or revocation list was rejected: a compromised server can withhold any signal it relays, so the real defence is that hosts take the newest signed release and can never be pushed back (docs/release-keys.md).
40. **The evidence pack says what its clocks measure.** Organisations set their own remediation deadlines per priority (NIST SI-2's "organisation-defined"), shown in the pack; each finding is held to the deadline in force when it was detected, read from the ledger, so relaxing one later can't turn an old miss into a pass; Cyber Essentials' 14 days stays fixed. Mappings added for SOC 2 CC7.1 and CC8.1 (CC8.1 from the approvals actually recorded on each remediation job) and NIS2 Art. 21(2)(e). Times run from first detection, not the vendor's release date (PCI 6.3.3 asks for the latter), and the pack says so instead of implying otherwise.
41. **Confirm only what's high-stakes or hard to undo (UI round 1).** Switching the trust ladder to Auto, revoking an API token, removing someone or changing their role, signing out everywhere and cancelling a fix ask first, all through one `ConfirmDialog`; the browser's own `confirm()` is gone. Choosing a trust-ladder mode only selects it (arrow keys move through radios, so saving on change could turn on Auto by accident); Save applies it. Low-stakes per-machine settings (criticality, ring, internet-facing, health units) keep saving as you change them and say "Saved. Findings re-ranked." A per-machine edit form was rejected: more code for the same safety.
42. **One set of shared components in `web/src/ui.tsx`.** Buttons, inputs, chips, switches, tags, alerts, "Saved" messages, fields, loading states, status pills and dialogs live in one place; pages don't define their own. Admin-only actions stay focusable with `aria-disabled` and point to one visible "Read-only" note, because a disabled button with a `title` can't be reached by keyboard or touch.
43. **Square stays.** The identity is ink on paper with square corners and crimson only for "fix now" and KEV. The stray rounded chips, pills and skeletons were squared off; `rounded-full` is kept only for real circles (the switch). The remaining `rounded-*` classes do nothing under the zero-radius tokens and were left alone.
44. **The server says whether a fix is already in flight.** `/api/summary` actions carry `asset_ids` and the newest active `job`, so Home links to it instead of offering "Plan fix", which the API refuses while a job is active. Failed jobs aren't included: they're listed under "needs a look" and can be planned again.
45. **Evidence says "no activity" rather than "met" when there was nothing to assess (owner decision, 2026-10-28).** For controls that are only about timeliness (Cyber Essentials update management, NIST SI-2, CIS 7.3/7.4) a period with no fixes and nothing overdue, and for SOC 2 CC8.1 a period with no changes, is `no_activity`. An auditor reading a signed pack shouldn't have to work out that "met" meant "0 of 0". Controls that include monitoring (ISO A.8.8, RA-5, CC7.1, NIS2) or make a true negative claim (PCI 6.3.3) keep met/not met. Overdue findings always mean `not_met`. 56. **Fixes obey time and topology (plan T13, T14, T40–T43, decision 12).** An approved job is handed out only inside

    Windows job is therefore the restart deadline plus 4 hours, not 2 hours (a Windows host that dies is flagged later). No install starts on battery

69. **`doctor` only reads, and the local log starts only behind the lockdown (2026-11-02).** `doctor` runs on hosts that are already in trouble, so it runs no lockdown, writes nothing, and sends no key: a config planted in an unlocked folder gets one keyless GET and nothing else. The folder's permissions are compared by SID (decision 68). A stopped Windows Update service passes and only a disabled one fails, because `wuauserv` starts on demand and stops itself when idle, so failing on "stopped" would flag healthy machines. The log is written only by `report`, `remediate` and `resume-job`, after their lockdown has succeeded: SYSTEM appending through a link planted before the lockdown could write to any file. `collect` never touches it, since self-update's self-test parses that output and runs on a host where the folder may be unlocked. It's a few lines rather than `RotatingFileHandler`, which holds the file open for the run: on Windows that blocks rotation by the job poll while a job runs, or by the new agent while the old one waits for it. Each write opens, appends and closes, and any failure is dropped. Agent keys and tokens are removed by value and by shape, since error text can echo whatever a server sends. Uninstall needs no change because the log lives in a state folder it already removes.
70. **The per-KB view judges a host by its build, and its canary by this update (2026-11-02).** "Who's missing October's update" could count open findings, but a host whose findings are risk-accepted would then read as patched, so a host has an update when the build it last reported reaches that KB's fixed build; a host on the hotpatch track has it when none of its CVEs is still on the host (52). Rows are per product and KB, because one KB can span products with different builds and a job's action key is per product; only each product's newest three show, since cumulative updates make older rows repeat who's behind. Reasons come only from jobs and facts: no job reads "No job yet", and facts such as WSUS are listed beside it, not claimed as the cause. "Plan the rest" plans canaries first and the rest once a canary has soaked. It counts only jobs reaching this update's build, whereas `canary_ok` looks at the whole action key, so September's canary success would open October's auto rollout and an old failure would halt every later month: that's existing behaviour, left alone here and worth its own decision. Planning changes no approval rule. Months come from a new `released` field on MSRC records and aren't guessed: records stored before it read "Cumulative KB…" until their MSRC document is next revised.
71. **Vulnerable drivers by exact file hash, reported as inventory rows (2026-11-02).** LOLDrivers' repository (`magicsword-io/LOLDrivers`, the source of `loldrivers.io/api/drivers.json`) is under "Apache License Version 2.0, January 2004" with no NOTICE file, so the list can be fetched and stored; the test fixture keeps a copy of the licence beside it. Every entry in the feed says "Exact file/Authenticode hashes only for blocking; Tags are hunting names", and that's the rule here: a finding opens only when a file's SHA-256 is listed, and a driver's name is never evidence. The server keeps the hashes in one row, refuses a changed format (an unknown category, a bad id, under 1,000 hashes) and keeps the last list. Left out on purpose: the 77 of 713 entries LOLDrivers hasn't marked verified, and the 105 of 2,430 samples with only an Authenticode hash. The agent's list is closed (decisions 7, 27): the server never sends it a path, a hash or a name. It hashes loaded drivers (CIM `Win32_SystemDriver` by `Started`, no translated words, decision 68) and `*.sys` directly in `System32\drivers`, because a planted driver isn't loaded until it's used. Not seen: a driver whose service was deleted after it loaded, a file elsewhere that isn't loaded, and a listed driver re-signed so its file hash changed. Caps: 128 MiB a file (a larger file can't be one seen before, since a listed hash means a listed size), 3,000 files, 180 s, loaded drivers first. Expected cost, not yet measured: a few hundred files and a few hundred MB read once per report (every 6 hours) by a process already running as SYSTEM, some seconds, and a few hundred more rows per Windows host. They're `InstalledPackage` rows rather than facts, because facts are capped at 64 KB and 500 items and go out with every asset in `/api/assets`: hundreds of hashes could push out the host's other facts and would make that list tens of MB at 1,000 hosts. A scan that failed or stopped early (`driver_scan.complete` false), or an agent that can't say, closes nothing: the rows are missing because they weren't read, not because the file went. Score: malicious fix-now; vulnerable and loaded next (70); vulnerable and only on disk planned (45), since loading it takes admin rights. Nothing removes a driver for you, because that can stop a machine booting. `sandbox/windrivers.py` is the VM proof: the file is placed, never loaded.
72. **Machine certificates and listening ports are facts the agent reads; a listener only raises a product we already matched (2026-11-02).** Certificates: the first 30 in the machine's Personal and WebHosting stores, read by OID and number (decision 68), with findings only for those with a private key, since without one the machine can't present it. Expired, an RSA or DSA key under 2048 bits, and an MD2, MD4, MD5 or SHA-1 signature each make one finding that lists them, so a server with 20 old certificates gets one line for each problem. A self-signed certificate's own signature doesn't count, because nothing relies on it. The Root and CA stores aren't judged: Windows itself ships expired, SHA-1 and 1024-bit roots on purpose for old signatures, so those checks would fire on every host. A key type .NET Framework can't read is "can't tell", which includes every elliptic curve key. **Dropped: roots not in Microsoft's list.** CCADB publishes Microsoft's program as a CSV with SHA-256 fingerprints (550 roots on 2026-11-02), but it covers the root program and has no entry for `Microsoft Root Certificate Authority 2011`, which Windows' own updates chain to, or `Microsoft Authenticode(tm) Root Authority`. Every host would then get a finding unless we wrote our own list of exceptions from memory, which is the guess this was meant to avoid. Listening ports: TCP only, by `Get-NetTCPConnection` and `Get-Process` (enum state and process name, neither translated), non-loopback, at most 60 (facts have to fit 64 KB alongside the jar scan's locations, or the whole report's facts are dropped), each with the firewall as `off` (off on any profile, the cautious reading), `allowed` (an enabled inbound allow rule in the active store covers that port and program), `blocked`, or null (rules unreadable). Rule scopes such as remote address and block rules aren't weighed, so `allowed` means a rule permits it, not that the internet can reach it. A listener adds 15 points through `risk.context`, with the reason shown, only when `allowed` or `off` and only on a finding for a product named in `winconfig.LISTENERS`. It opens no finding, and an unmatched process changes nothing. Runtimes (java, node, python) aren't in that table because the name doesn't say which product is listening, which also leaves out Elasticsearch, and UDP isn't collected because most UDP endpoints are short-lived clients. 80. **The agent says what it read, and the server decides what follows (engine slice, 2026-11-03).** Failures used to end in an empty list, so a refused registry key and a host with nothing installed sent the same report and got the same clean answer (R4.3). Each inventory now carries a collection document: per source, `ok`, `partial` or `failed`, a count and a short error. The state comes from the exception type and error code, or an error category in PowerShell, never from translated text (68). It's a judgement-free report: "an empty Uninstall list can't be real" and "fewer packages arrived than were read" are the server's calls. The server drops a document that breaks its bounds and keeps the packages, as with facts, and never keeps the last report's: a stale "ok" describing new packages is the false clean this exists to stop. No document reads as unknown, so an old agent gets `not-run`, never `not-applicable`.
81. **A scan's content version names what that host's evaluation consulted, and the report writes its record when asked (engine slice, 2026-11-03).** Advisories are updated in place, so "the feed version" isn't a thing we have. Hashing the whole table on each report would be slow and would change hourly for hosts it doesn't concern. So the version is the newest date in the advisories this host's checks read, plus a hash of them, KEV, NVD scores and the app version. Equal versions mean identical input (T34); two hosts usually have different ones. The content itself isn't stored, so the record explains a result and replays only while the advisories are unchanged. `GET scan-report` writes on read because evaluating on every inventory would cost every agent report during a slice that's only proving parity. Repeat calls store nothing new, and each host keeps its latest 20 records. When `rescan` moves onto the engine the record should move with it.
82. **Where the engine won't match `rescan`, on purpose (engine slice, 2026-11-03).** Whether a version is affected is always `match_package`'s answer, so the numbers can't drift. Three differences are deliberate and are listed by the parity check or the report. A Windows fix naming another build number is `undetermined` (R5.3), where `rescan` compares it. `rescan` closes a finding when its package leaves the inventory, even when the read failed; it's unchanged in this slice, so the report lists such findings as `not-reassessed` until that moves (R4.6). A source that's only partly read lowers every reading from it to `unverified` and makes its products `undetermined`, including ones the failed part didn't touch: Defender's status not being read also marks .NET. That's cruder than it should be, chosen so a partial read can never pass as a clean one. Splitting sources further should wait for measured false-negative rates per grade (R6.2).
83. **A Linux package list that wasn't read in full doesn't replace the last one (engine, Linux slice, 2026-11-03).** The agent used to refuse to send an empty or failed read. That kept `rescan` from closing every finding on silence, but the server never heard of the failure. Now the agent sends what it read with the query's exit status, and the server decides (80): when the `package_db` source isn't `ok`, or holds nothing, the inventory endpoint keeps the stored packages. `rescan` then behaves as if nothing arrived, and the engine judges none of them, because they aren't this read's, and carries open findings as `not-reassessed`. A partial read is treated the same, so a cut-short list can't make missing packages look removed (T3). Windows still replaces its lists (82). On Linux the package list is the whole inventory, so closing on a failed read would close everything. Agents only update to the release their server relays (31), so only a hand-installed new agent could send such a list to an old server. Seen on the first real runs: with the package database moved aside, `dpkg-query -W` on Debian 13 and `rpm -qa` on AlmaLinux 9 both exited 0 and printed nothing, so the exit status alone can't catch it; the server's "an empty list can't be real" rule did.
84. **On Linux a check is a source package and version against the distribution's own advisory, and every package the release has advisories for gets a verdict (2026-11-03).** Binaries built from one source share its advisories, so they're one install; two versions of one source (an upgrade half done, two kernels) are two (T19). The package database read directly, against the distribution's own record (OSV carries Debian's tracker, Ubuntu's notices, AlmaLinux's errata), is `confirmed` (design-e2.md). A package no advisory names isn't a check. One the release has advisories for and that isn't installed is `not-applicable`, which is why only a fully read list is judged at all. Refusals over guesses (4): a version dpkg or rpm would never install is `undetermined`, because the comparators order any string. A modular RPM is compared only with fixes for a module of the same major version, since the advisories don't name the stream. Two streams of one major version (nginx 1.22 and 1.24) still compare until they do. Unfixed records stay `vulnerable`: Debian's `unimportant` urgency is `no-fix-planned`, the rest `no-fix-yet` (R7.5). Architecture isn't checked, as none of these feeds states one. Found on the first real Debian 13 run: a binary can carry a version its source doesn't (util-linux 2.41-5 ships `bsdutils` as 1:2.41-5 and `login` as 1:4.16.0-2+really2.41-5), and the epoch puts it past every fix, so both `rescan` and the engine read those two as `not-vulnerable` while their source was vulnerable. Fixed: the agent sends `${source:Version}` beside the binary's version where they differ (a binNMU's `+b1` too), the server stores it in its own column, and both compare it, so those binaries join util-linux 2.41-5 and are judged with it. The report still names each binary's own version, and upgrades still use it. A row stored before this, or sent by an older agent, has no source version and is compared by its own, as before. RPM keeps the binary's version: `%{SOURCERPM}` gives the source's version and release but not its epoch, which RHEL-family fixes carry (openssl's `1:`), so a version built from it would misjudge every package with an epoch. A subpackage takes its parent's epoch, version and release unless its spec sets its own, which is rare (perl's bundled modules), and that rare case isn't handled. apk can't differ: abuild gives every subpackage its origin's version and release, and Alpine has no epochs.
85. **Kernels, end of support and pending reboots on Linux (2026-11-03).** A kernel package is matched to `uname -r` by each distribution's naming. One that's installed but not running is its own marked state and is still judged, since it matters once booted. A vulnerable running kernel with a newer installed one that's fixed says "restart into it". A running kernel no package provides (WSL, containers, custom builds) is `undetermined`: the distribution's advisories don't describe it. End of support uses endoflife.date's cycles, already fetched for apps. Its `eol` for Debian includes LTS, whose fixes are in the same feed; for Ubuntu it's standard support, because ESM fixes are in Ubuntu Pro feeds the agent never reports. It's judged as of when the inventory was read, so the evaluator stays clock-free (T34). Past it, the release is an `EOL:` finding graded `reasonable` (a third party's summary of the vendor's page), and every `not-vulnerable` becomes `undetermined` while `vulnerable` stays (R7.6). Only the engine does this; `rescan` has no Linux end-of-support findings, so parity lists it as explained. A pending reboot is reported where the distribution states it (the reboot-required flag when its writer is installed, `needs-restarting -r` on RPM distributions) and is otherwise unknown.
86. **The network slice is a prober inside the engine model, and scope is proven once before any packet (2026-11-03).** The outside-in checks were ad hoc: `external.checks` ran a port sweep and TLS probe and `external.scan` turned the results straight into findings. The engine's remote path (`engine/network.py`) is the spec's Prober (section 14): target and declarative rules in, verdicts with evidence out, budgeted and scoped. The mandatory gate moved to `external.prove_scope`, called by both `scan` and the prober, so the ownership rules (DECISIONS 28) are enforced in exactly one place: it re-proves the name and the address, refuses anything but a public address, and returns the single IP every connection goes to, including for anything resolved mid-scan (R2.9). No packet is sent before it passes. Budgets are the engine's, not the check's: per-host and per-endpoint concurrency (declarable down to one connection to an endpoint, T26) and a per-check deadline that yields `not-run: timed-out` (R2.4). Safety is a class on each rule; safe mode refuses disruptive rules and the rule data carries no field that could turn it off (R2.6). As with the host engine, findings still open and close through `external.scan`; this is a parallel read until a later slice moves them over, and `parity` lists the engine-only checks.
87. **No remote check is ever `confirmed`, a refused port is positive evidence, and a dropped port is never clean (2026-11-03).** A remote probe reads the host from outside, so it can't reach `confirmed`, which means the host's own state read directly (design-e2.md). Exposed-service and TLS verdicts are `reasonable` (reachability and the certificate are observed directly, but not authenticated against the host); a banner-to-CVE result is `unverified` (a banner is remote and spoofable, R10.2), and each says an agent or credentialed reading would raise it. The three port states are kept apart, which the old boolean `port_open` conflated: accepted is `vulnerable` for a risky service, refused (RST) is `not-vulnerable` — positive evidence that nothing listens — and a firewall drop (timeout) is `not-run: port-filtered`, never a clean result, because it proves nothing either way (spec R4.2). 443 refused is `not-applicable` (no HTTPS to assess); 443 dropped is `not-run`. The exposed-service and TLS verdicts reuse `external`'s own `exposed_finding` and `tls_findings`, so the prober and the shipped scan can't disagree on what's vulnerable (parity by construction).
88. **Every active probe carries a negative control, and a port that answers everything is suppressed, not fingerprinted (2026-11-03).** A declarative web-path rule (spec section 5 kind 4) learns how the site answers a path that can't exist before it trusts a page being served: a site that returns success for the random control is a soft-404, and its web-path checks are `undetermined: soft-404`, said out loud (R10.3, T22). A finding needs a flaw-specific marker in the body and a response that differs from the control. Product identification by banner gets its own negative control: a unique nonce a genuine service won't echo. A port that reflects the nonce is a catch-all, tarpit or honeypot, so every product and version result from it is suppressed and the report says why (R10.5, T23) — this is kept off the exposed-service reachability checks, which read no banner and so can't be fooled this way. Probes are read-only (GET, connect, read): no writes, nothing left behind (R10.4).
89. **A banner-to-CVE check only where the vendor ships full-version releases, and a distribution-tagged banner is declined (2026-11-03).** Banner version-matching is the commercial-scanner noise source this product set out to avoid (DECISIONS 28), so the handful of checks are chosen, not scraped: vsftpd 2.3.4 (CVE-2011-2523, a one-off trojaned upstream tarball, never a distribution package), ProFTPD 1.3.5 mod_copy (CVE-2015-3306, fixed as the new upstream 1.3.5a), and OpenSSH regreSSHion (CVE-2024-6387). Each product states its upstream version in the banner and fixes by releasing a new full version rather than backporting into a fixed package string. An OpenSSH banner that carries a distribution's own build suffix (Debian, Ubuntu, `+deb`, `elN`, `.fcN`) is declined as `undetermined: backported`, not guessed, because the distribution backports the fix without changing the number (R10.2). All three are `unverified`: a banner is remote and spoofable, and an agent reads the real binary. Limits: the list is deliberately tiny, the banner is trusted weakly, and a spoofed banner produces a weak-grade false positive, which the grade is there to carry.

95. **A host far behind steps through the old update Windows Update offers, found from MSRC (2026-11-03).** A fresh Server 2022 evaluation install (20348.587, 2021 media) was offered only 2023-11's KB5032198 and a .NET update, so the job for the newest KB and decision 67's next-newest step both stopped with "No changes made", and the server, which syncs only recent MSRC months, knew no KB that could move it. To run on the hourly re-match too (it took 585 s for 1,000 hosts when it loaded its own advisories), the engine shares that pass's cache: decoded records, per-product KEV and CVSS, the distro's package universe, the "feed loaded" probes, one ledger read per org for SBOM subjects, each product's digest for the content version, and each install's judgement. `perf.py` at 1,000 hosts (`last_run_perf_sqlite.json`): the hourly re-match with the engine takes 32.5 s (29.2 s without it; the gate was 35 s), and ingest median is 0.72 s (it was 1.30 s, since the shadow no longer re-reads and re-hashes every advisory). Within a pass, advisories, KEV and CVSS don't change, so this changes no verdict. It does change the content version's format once, so each host stores one extra scan record. The judgement memo holds every distinct install's verdicts for the pass, which costs memory in a fleet with few shared versions.
124. **Findings close only on evidence: phase 4 of `tasks/plan-engine-findings.md`, plus a weekly check against OSV's live answers (2026-11-09).** In the engine's slice, a finding `rescan` no longer matches closes only when the engine proves it absent: not vulnerable at the installed version, or not applicable. Anything else leaves it open, with one "Still open: …" line in its reasons saying why (for example, a Python package scan cut short used to close a `requests` finding on that silence). To keep "not installed any more" from getting stuck open, the engine now gives a prior finding `NOT_APPLICABLE` with reason `removed` when its product isn't installed and every source that would list it was read whole (`_read_in_full` in `engine/evaluate.py`): the distro's package list (plus `os_release` after a release upgrade), `windows_build` (a feature update renames the OS product), `scan.READ_FROM` for Windows apps and Microsoft products, the agent's language-package scan, or the SBOM. A product that's still installed, but whose advisories no longer carry the finding's id (withdrawn, or re-keyed when a GHSA gains a CVE), is `NOT_APPLICABLE` with reason `withdrawn`, so it doesn't stick open beside its new id. A fixed version on a release past end of support closes too: end of support stops new advisories, it doesn't undo a fix. The independent review of #45 tightened what counts as read in full: Microsoft products also need `user_hives` (per-user installs) and `windows_build` (.NET and Store names carry the OS's); the OS needs a recognised OS install, since an OS name MSRC doesn't map isn't an upgrade; and on Linux an agent language scan also needs `package_db`, since a list read short keeps the old app rows. A host's SBOM finding can still stick open when the agent's own scan for that ecosystem is off (the safe direction). An old agent without a collection document can't say what it read, so it keeps the earlier rule. A Linux package list read short already never replaced the last (DECISIONS 83), so distro findings change least. Out of the slice (settings, drivers, end of support), nothing changes. Second, parity can't catch a fault `rescan` and the engine share (`match_package`, the comparators), so `test_match.py` now also runs the engine against OSV's own answer for each of the 49 fixture cases. `.github/workflows/oracle.yml` re-fetches those answers from the live OSV API every Monday and runs both tests; on 2026-11-09, 11 fixtures had changed upstream and all 112 tests still agreed. The Windows Update oracle needs VMs and stays a sandbox run (`sandbox/winoracle.py`). Cost: the hourly re-match at 1,000 hosts is 32.6 s (32.5 s in phase 3). A first cut built the installed set for every unanswered finding and took 35-37 s; now it checks the sources first, once per ecosystem, and builds the set only when they were read in full. Real hosts: Debian 13 297/297, AlmaLinux 9 54/54, Windows 11 1,038/1,038, 0 `engine_disagrees`.
125. **The engine alone decides which findings exist in its slice: phase 5 of `tasks/plan-engine-findings.md` (2026-11-10, the owner's decision on agents without a collection document).** `rescan`'s own matching loop, its comparison with the engine (`engine_disagrees`) and `NIMSTEAD_ENGINE_FINDINGS` are removed: one release (0.7.8) ran after phase 4 with no disagreement, and the last shadow runs on agent 0.6.9 read none (Windows 11 1,035/1,035, Debian 13 301/301, AlmaLinux 9 54/54, language packages 1,024/1,024 and an SBOM 53/53). Inside the slice a finding opens only on a `vulnerable` verdict; no decision means nothing opens, and if the engine raises, nothing opens or closes on that host. An inventory without a collection document (agents older than 0.5.0) is no longer judged at all: the engine returns one `not-run` verdict with reason `no-collection-document` ("update the agent"), and that host's open findings stay open with that reason. They are never closed on silence. The alternative, judging it graded unverified, would have kept a second closing rule for the oldest agents forever, and none are known to be running (DECISIONS 123: no real hosts yet). SBOM application assets have no agent and are unaffected. Hand-written test and seed inventories now carry the document a current agent sends (`sandbox/agentdoc.py`; the API tests add it unless a test sends `"collection": None` on purpose). Seeding perf with documents exposed a cost real agents had always paid: `Inventory.source()` counted the whole package list on each call, once per install. Counts are now made once per inventory, and three more per-host costs that every documented host paid went with the gate in view: each install's source state is read once per inventory, a product's advisory records are indexed by id once per feed pass instead of being scanned once per finding per host, and of a host's ~20,000 verdicts only those that could answer an open finding are keyed when carrying findings forward (a verdict keeps its report-order key, since most are shared across the pass). `perf.py` at 1,000 hosts, every host now sending a document: ingest median 1.01 s (gate 1.56 s), hourly re-match 33.7 s (gate 35.0 s, the plan's 29.2 s + 20 %; 32.6 s at phase 4, when the seed's hosts had no document and the engine judged nothing on them). With documents on both sides at 100 hosts, phase 4's code took 1.24 s and 22.2 s. PostgreSQL 17: the suite passes. `parity.compare` stays, now checking a host's findings table against its verdicts in the sandbox harnesses. The same harnesses on the final build: Windows 11 1,038/1,038 (plus 9 settings), Debian 13 302/302, AlmaLinux 9 54/54, language packages 1,025/1,025, SBOM 53/53, none unexplained. Counts moved from the earlier runs because the hosts did: OSV gained one Debian advisory, and a fresh Windows VM had Defender and the Windows Security app at versions now vulnerable. To compare builds without that drift, each harness keeps its database after the full inventory and `sandbox/engine_replay.py` re-judges it from nothing: 0.7.8's code and this build open identical findings, row for row with versions and status, on every one (Windows 11 1,047, Debian 13 302, language packages 1,025, the SBOM 53, the same host after its scans were cut short 984, AlmaLinux 9 54), Defender's included.
126. **External targets are scanned by the engine's prober, once, and their findings close only on evidence (2026-11-11, tasks/plan-network.md N1-N2).** `external.scan` ran its own port sweep (`external.checks`) and resolved any finding it no longer saw, so a firewall that started dropping 3389 closed an exposed-RDP finding on silence, the gap phase 4 of the engine track closed for hosts (DECISIONS 124). The scan now gets its observations from `engine.network.probe`, one pass per scan (the old sweep is deleted, so a target gets no extra traffic), opens findings from the exposed-service and TLS verdicts (which call the same `external` helpers as before, so what opens is unchanged), and stores the engine's report as a `ScanRecord`, which `GET /api/assets/{id}/scan-report` returns for a target (it never probes). A finding closes only when the engine proves it absent: the port refused the connection, or the TLS handshake ran and no longer shows it (or nothing listens on 443). A filtered port, a timed-out check, a target that stopped answering, or legacy TLS this scanner can't offer keeps it open with one "Still open: …" reason, as on hosts. A TLS handshake that was cut, reset, timed out or refused with a TLS alert is undetermined too (`host-lost`); only a reply that isn't TLS at all (OpenSSL's `WRONG_VERSION_NUMBER`) is "not a TLS service". A refused current handshake then tries TLS 1.0/1.1, so a server that speaks only those opens `NIM-TLS-LEGACY`, its certificate reading `legacy-only` (unread, so no other TLS finding closes on it). A device certificate the server can't read (over 16 KiB, or malformed) counts as lost too (found by the reviews after N11). No shadow release: the host track needed one because two matchers could disagree, and here the verdicts are built from the same helpers. The prober reads more ports than the old sweep (banner and HTTP ports too), so a fully firewalled target takes longer per scan; budgets are unchanged (8 workers, 3 s connect, 8 s per endpoint).
127. **A vulnerable version read from a service banner opens a finding, graded unverified and ranked below firmer evidence (2026-11-11, N5; the owner said to choose what an industry-leading tool would do).** Commercial scanners report banner matches; leaving them out would miss a backdoored vsftpd or an unpatched OpenSSH that answers the internet. They are weak evidence (a banner can be spoofed, and distributions backport fixes without changing the number), so each keeps the engine's `unverified` grade and says an agent reading the host would confirm it; its likelihood input is 0.4 where exposed services use 0.8, so a CVSS 9.8 banner match ranks below an exposed Telnet (9.0) read directly. The engine's suppressions stay in front: a port that echoes a nonsense probe (a catch-all) and a distribution-tagged OpenSSH banner open nothing. External findings are now keyed by vulnerability and endpoint, since one banner CVE can be on two ports. A banner finding closes when its port refuses, or answers with a greeting that no longer names that product or names a fixed version; a dropped port keeps it open. KEV and EPSS aren't applied to banner CVEs yet: the external scorer has no advisory lookup, and a weak match shouldn't be promoted to fix-now by KEV alone without one.
128. **Devices with no agent are found passively, from each agent's own neighbour table, and named by the IEEE registry (2026-11-11, N6-N8; the owner said to choose what an industry-leading tool would do, and not to wait on the pentest).** Discovery tools list the devices on a network that no one manages; scanning for them would mean the server telling agents to send packets, which DECISIONS 7 and 27 don't allow (N9 asks that question separately). Every machine already holds a table of the addresses it has talked to on its links, so agent 0.7.0 reports it, read only, from a fixed collector (`/proc/net/arp` and `ip -j neigh` on Linux, `Get-NetNeighbor` on Windows), with its own interface addresses and MACs so the server can tell a neighbour that is another managed machine. The server stores rows per reporting host (a host's key writes only its own rows; what a compromised agent can still do is in DECISIONS 130), drops what doesn't fit row by row rather than refusing the inventory, and deletes rows unseen for 30 days, since MAC addresses of personal devices can be personal data. `GET /api/network/unmanaged` groups by MAC (DHCP moves addresses) and leaves out any MAC or address an agent reports as its own, including Windows' `addresses` fact (DECISIONS 112). Vendor names come from the IEEE registry as Wireshark publishes it for automated download (IEEE's own file refuses ordinary HTTP clients, and we don't disguise ours), fetched only weekly, as that file asks, and only once any agent has reported a neighbour; a locally administered MAC reads "randomised MAC" rather than a guess. The table can be turned off per host with `"neighbours": false` in the agent's configuration. The collector is added to the pentest scope.
129. **One locally opted-in agent checks the devices on its own subnet for exposed services, and the agent alone decides what it touches (2026-11-12, N9; the owner: "proceed with best recommendation").** The passive list (DECISIONS 128) can't say whether that camera has Telnet open; internal scanners can. A host enrolled with `--allow-network-checks` (a local flag the server can't set, like `--allow-remediation`) runs, after each report (every 6 hours on its own timer; the server can't trigger it), the signed agent's fixed checks against up to 32 devices from its own neighbour table that sit in private IPv4 subnets it is directly attached to (/16 or smaller), rotating through them run by run. The server names nothing: no addresses, ranges, ports or rules, so a compromised server gains no way to aim it. The checks are the external prober's read-only set (TCP connect on the fixed ports, the greeting and nonce echo test on banner ports, one TLS handshake and a TLS 1.0/1.1 attempt on 443, and the negative control plus `/.git/config` and `/.env` on 80), one connection per endpoint, each run capped at 5 minutes. The agent sends observations only; the server judges them with the same engine evaluator, drops any device that isn't in that host's own stored neighbour rows, and keeps each check in the ledger. Internally an open SMB, RDP or database port is normal, so only services that are cleartext or unauthenticated by default (Telnet, FTP, VNC, Redis, Elasticsearch, MongoDB, Memcached, the Docker API), certificate expiry and legacy TLS, the two web paths and banner versions become findings; an untrusted or name-mismatched certificate isn't one (internal devices are usually self-signed and reached by address). Findings live on a `device` asset per MAC (not a machine with an agent, so it's left out of the machine list and agent alerts), score as not internet-facing, and close only on evidence (DECISIONS 126). What a compromised server could still do: it can't choose targets or run more often. What a compromised host can do, and the review that narrowed it, is in DECISIONS 130. IPv6 neighbours aren't checked yet.
130. **The ship review of network services: findings change only on one machine's own evidence, and what a compromised host can still do (2026-11-12; the owner said fix all listed).** Three reviewers (code, security, tests) found ways a finding could still close, duplicate or hide without evidence, and that decisions 128 and 129 overstated what a compromised agent couldn't do. Changed: (1) each machine that checks a device keeps its own view (a device asset per checking host and MAC), so one machine's report never closes what another found, honestly (a firewall that refuses one VLAN) or not; (2) a host's claim that a MAC is its own counts only where that MAC was seen at one of the host's own addresses, and the address fallback for older agents matches a device's latest address only; (3) the agent judges `/.git/config` and `/.env` itself and sends only status, marker matched, body SHA-256 and had-content, so file contents never reach the server; anything the server can't read is no response; device web findings are named by port, so a new address keeps them; (4) a banner finding closes only on a positive greeting that no longer names the product, not on a refusal or a cut-off line; (5) the agent starts each run at a random point (a clock rotation lined up with the 6-hour timer and skipped half of 64 devices), and every read, device and run has a deadline on daemon threads, so a device can't stall reporting; (6) limits per organisation on check reports and the device list, capped neighbour rows per host and per org, the 30-day prune in the hourly run, and no device address or MAC in the permanent ledger; (7) devices stay out of asset counts, attack paths and the palette, and explain themselves as on-your-network. What a compromised host can still do: report false observations, which change only its own view of a device; claim an address and MAC pair it doesn't own, which makes that device look like the host (shown as it, so not hidden from view altogether); and add rows to its own neighbour table, within the caps. It still can't read or change another host's data, aim another agent, or reach anything outside its own network.
